==================================================
PROBLEM TO FIX
==================================================

Notification handling may be inconsistent across runtimes and may lack one strict contract for:

1. duplicate notifications;
2. expiry after the configured lifetime;
3. tenant isolation;
4. read/unread updates;
5. deletion or dismissal;
6. safe response DTOs;
7. stable status and error handling.

The product requirement is:

- no duplicate notifications;
- notification expiry after 24 hours unless existing code clearly defines another duration;
- every notification remains restaurant-scoped;
- notification data must include safe context without exposing internal fields.

==================================================
OBJECTIVE
==================================================

After this task:

1. One canonical notification service handles creation, listing, read-state updates and dismissal.

2. Duplicate notifications are blocked deterministically.

3. Notifications expire according to one explicit TTL policy.

4. Expired notifications are never returned as active.

5. Wrong-tenant users cannot read or mutate another restaurant’s notifications.

6. Client-provided restaurant ID, role, user ID or notification ownership is not trusted.

7. Vercel, Express and Vite use the same notification contract.

8. Public/internal response DTOs do not expose raw database rows.

9. Existing Prompt 8–26 regressions remain green.

==================================================
