==================================================
CONFIRMED DEFECT
==================================================

Current client-IP resolution may trust the first value supplied through:

x-forwarded-for

without proving that the request passed through an approved reverse proxy.

Consequences:

1. A direct caller may supply a fake forwarded IP.

2. Rate limits may be applied to an attacker-selected identity.

3. Abuse controls may be bypassed by rotating spoofed headers.

4. Audit records may attribute requests to the wrong source.

5. Vercel, Express, Vite, Cloudflare and local development may interpret IP headers differently.

==================================================
OBJECTIVE
==================================================

After this task:

1. One canonical client-IP resolver is used everywhere.

2. Untrusted forwarding headers are never accepted as authoritative.

3. Each supported runtime has an explicit trusted-proxy policy.

4. Direct connections use the actual socket/connection address.

5. Forwarded chains are parsed and validated safely.

6. IPv4 and IPv6 addresses are normalized consistently.

7. Rate limiting and abuse controls use the canonical resolved identity.

8. Spoofed forwarded headers cannot change the effective client identity.

9. Logs and responses never expose internal proxy chains or configuration.

10. Prompt 18 Redis protection remains fully fail closed.

==================================================
STRICT RULES
==================================================

Do not:

- trust arbitrary x-forwarded-for values;
- automatically trust the left-most forwarded address;
- trust a header merely because it exists;
- use browser/client-provided runtime flags;
- accept client-provided IP values in request bodies or query parameters;
- silently fall back to a spoofable header;
- disable rate limiting when IP resolution fails;
- treat every unresolved caller as one permanent global IP;
- expose proxy IPs, private infrastructure addresses or full header chains in API responses;
- log authorization headers, cookies, secrets or Redis credentials;
- add a third-party IP parsing dependency unless the repository has no safe native option;
- modify unrelated business logic;
- add Agent-memory files, screenshots, attached assets, pasted prompts or generated reports.

STEP 2 — DEFINE THE TRUST MODEL
==================================================

Define one explicit server-side trust model.

Supported modes should be derived from actual repository runtimes, such as:

- direct/local;
- trusted hosted proxy;
- Cloudflare-fronted deployment;
- test.

Requirements:

1. The mode must come from trusted server configuration or reliable runtime detection.

2. A public request header must never select the trust mode.

3. Direct/local mode must ignore forwarded headers by default.

4. Hosted-proxy mode may use only the platform-approved client-IP source established for that runtime.

5. Multi-hop forwarded chains must be processed using a documented trusted-hop rule.

6. Unknown or contradictory proxy configuration must fail safely in production.

7. Development behavior must be explicit.

8. Tests may inject a controlled resolver context.

Do not enable a broad “trust every proxy” setting.

==================================================
STEP 3 — CREATE ONE CANONICAL RESOLVER
==================================================

Create or repair one shared function equivalent to:

resolveClientIp(request, runtimeContext)

The result should clearly distinguish:

- resolved;
- unavailable;
- invalid;
- untrusted-forwarding-data.

The resolver must:

1. Read the socket/connection peer address.

2. Read forwarding headers only when the immediate proxy/runtime is trusted.

3. Parse comma-separated chains safely.

4. Trim whitespace.

5. Reject malformed values.

6. Remove IPv6 brackets and permitted transport ports safely.

7. Normalize IPv4-mapped IPv6 addresses.

8. Normalize valid IPv6 representation consistently.

9. Reject control characters and oversized header values.

10. Never return a raw unvalidated header string.

11. Return a bounded canonical value suitable for rate-limit keys.

Use native Node.js IP validation where practical.

STEP 4 — DEFINE SAFE FAILURE BEHAVIOUR
==================================================

- Do not invent a random identity per request.

DEVELOPMENT/TEST

- Allow explicit injected identities only in test or controlled development setup.
- Do not use production deployable bypass flags.

Preserve Prompt 18 fail-closed behaviour.
