==================================================
CONFIRMED DEFECT
==================================================

Repository evidence indicates that owner demotion and deletion use logic equivalent to:

SELECT COUNT(*)
FROM restaurant_members
WHERE restaurant_id = ...
  AND role = 'owner'
  AND active = true
FOR UPDATE

This does not safely serialize last-owner decisions.

Problems include:

1. Aggregate results are not the underlying owner rows.

2. The query does not provide the intended row-level lock over the owner memberships.

3. Two concurrent transactions may both observe that more than one owner exists.

4. Each transaction may then remove a different owner.

5. Both operations may succeed and leave the restaurant with zero active owners.

6. Similar races may exist across:

   - owner deletion;
   - owner demotion;
   - owner deactivation;
   - membership soft deletion;
   - runtime-specific mutation paths.

7. A check performed outside the mutation transaction creates a time-of-check/time-of-use race.

STEP 3 — SELECT ONE SERIALIZATION STRATEGY
==================================================

Choose one PostgreSQL-backed serialization strategy based on repository evidence.

Preferred strategy:

PATH A — LOCK THE PARENT RESTAURANT ROW

Inside the same transaction:

1. Lock the restaurant row:

   SELECT id
   FROM restaurants
   WHERE id = $1
   FOR UPDATE

2. Lock the target membership row.

3. Lock or read all currently active owner membership rows.

4. Determine whether the proposed mutation would leave at least one active owner.

5. Perform the mutation.

6. Commit.

Every owner-sensitive operation for the restaurant must acquire the parent restaurant lock first.

Alternative:

PATH B — TRANSACTION-SCOPED POSTGRESQL ADVISORY LOCK

Use this only when a suitable parent restaurant row cannot be locked consistently.

Requirements:

1. Use `pg_advisory_xact_lock`, not session-level advisory locks.

2. Derive a stable restaurant-scoped key server-side.

3. Acquire the lock inside the database transaction.

4. Use the same key derivation in every owner-sensitive mutation.

5. Document collision and key-generation considerations.

6. Continue to lock the target membership row where appropriate.

Do not mix lock strategies inconsistently.

State in the final report which path was selected and why.
